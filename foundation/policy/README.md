# Azure Platform Foundation Policy Layer

The APF Policy Layer implements Governance as Code for Azure Policy.

## Ownership boundary

APF deliberately separates infrastructure ownership from policy ownership.

| Capability | Declarative owner |
| --- | --- |
| Management groups | Terraform / APF |
| Platform managed identities | Terraform / APF |
| Platform RBAC | Terraform / APF |
| Azure Policy definitions | EPAC |
| Azure Policy set definitions | EPAC |
| Azure Policy assignments | EPAC |
| Azure Policy exemptions | EPAC |
| Policy-assignment role requirements | EPAC |

Terraform must not manage policy resources that are owned by EPAC.

## Source of truth

Policy content remains Azure-native JSON/JSONC wherever practical.

APF consumes the Microsoft Azure Landing Zones Library as an upstream,
versioned dependency and layers APF-specific policy configuration on top.

Pinned versions live in:

    foundation/policy/versions.json

## Desired-state strategy

APF uses two explicit desired-state modes:

- Brownfield adoption starts with `ownedOnly`.
- Greenfield targets `full` after the intended policy baseline has been
  populated and reviewed.

A portal change is not a durable configuration change. A durable change must be
represented in source control.

## Commit 10 migration baseline

The legacy HCI policy library is classified against the pinned ALZ/SLZ
releases. The migration map is stored in:

    foundation/policy/migration/hci-foundation01-map.json

Legacy governance decisions such as `Audit` and `DoNotEnforce` remain visible
even when Microsoft now provides the underlying definition or assignment.

## Commit 11 plan-only pilot

The first executable desired-state profile is:

    foundation/policy/profiles/enterprise/
        audit-first-subscription-pilot.json

It deliberately contains only one subscription-scope assignment:

    APF - Audit public IP creation

This reuses the current Microsoft built-in policy and preserves the legacy
`CAF-Deny-Public-IP` behavior with:

    effect = Audit
    enforcementMode = Default

The pilot uses:

    desiredState.strategy = ownedOnly

and therefore does not claim full ownership of existing customer policies.

The subscription scope is temporary. Full ALZ/SLZ archetype synchronization
starts only after APF Level 1 establishes the management-group hierarchy.

Customer-side desired state is generated by:

    tooling/customer-policy/configure.py

The generated GitHub workflow performs `Build-DeploymentPlans` only. Commit 11
does not generate a Policy Apply workflow.
